# مدیریت منابع تطبیقی — v0.1.15

## انتخاب پروفایل

`hardware.resource_snapshot()` با psutil مقدار RAM قابل استفاده، مصرف CPU و هسته‌های
مجاز affinity را می‌خواند. در لینوکس محدودیت cgroup نیز لحاظ می‌شود. وجود provider
به‌تنهایی اثبات GPU نیست: CUDA/DirectML باید همراه با دستگاه فیزیکی پیدا شود
(nvidia-smi یا WMI/CIM ویندوز). اگر نشست واقعی به CPU برگشت، پروفایل downgrade می‌شود.
CPU-only ONNX Runtime معمولی، حتی روی دستگاه دارای GPU، به‌درستی Medium/Low می‌گیرد؛
نصب خودکار چند توزیع متعارض ONNX Runtime انجام نمی‌شود.

| پروفایل | شرایط | تایل LaMa | CPU threads/affinity | سقف pool | OCR |
|---|---|---:|---|---:|---|
| High | GPU قابل استفاده، RAM آزاد حداقل ۶ GiB و CPU زیر ۷۰٪ | 512 | نصف هسته‌های مجاز | 2 | detector ضلع حداکثر 1536، batch=6 |
| Medium | حداقل ۴ هسته و ۳ GiB آزاد، CPU زیر ۸۰٪ | 384 | نصف هسته‌های مجاز | 1 | detector ضلع حداکثر 960، batch=6 |
| Low | RAM کمتر، CPU شلوغ، هسته کم یا اطلاعات نامشخص | 256 | 1 | 1 | مدل همراه RapidOCR، detector حداکثر 640، batch=1 |

در شروع برنامه و پیش از هر job تشخیص انجام می‌شود. در حین job فقط downgrade مجاز
است؛ telemetry حتی در همان Low هم تازه می‌شود. ارتقا پس از آزادشدن منابع، فقط در
شروع job بعدی انجام می‌شود. زیر ۱ GiB خودکار Low انتخاب و LaMa کنار گذاشته می‌شود؛
زیر ۵۱۲ MiB آزاد، job فعال با پیام روشن متوقف می‌شود تا سیستم تحت فشار بیشتر نرود.

High از GPU و اجرای موازی گراف ONNX استفاده می‌کند. DirectML طبق محدودیت ORT در
حالت sequential/memory-pattern خاموش است. **تایل‌ها همچنان ترتیبی‌اند** تا چند نسخهٔ
مدل/accumulator هم‌زمان حافظه نگیرد. pool حداکثر ۲ slot دارد، اما قفل API فعلی فقط
یک job تصویری را در هر لحظه می‌پذیرد؛ ادعای پردازش موازی چند صفحه نمی‌شود.

## سازگاری مدل و کاهش کیفیت

تایل جزئی pad می‌شود، نه resize؛ مختصات اصل حفظ می‌شود. اگر مدل dynamic باشد،
واقعاً ورودی‌های ۲۵۶/۳۸۴ را می‌گیرد. اگر مدل ONNX ورودی ثابت ۵۱۲ داشته باشد، مدل را
با تایل ۲۵۶ به‌زور اجرا یا دوباره به ۵۱۲ بزرگ نمی‌کنیم: fallback کلاسیک حفظ می‌شود
و `inpaint.fixed_shape.fallback` ثبت می‌شود. در افت پروفایل، crop نیمه‌کاره با شبکهٔ
کوچک‌تر از نو ساخته می‌شود؛ اندازه‌های متفاوت مخلوط نمی‌شوند.

در Low، مدل OCR سرور و ComicTextDetector استفاده نمی‌شوند تا وزن دو مدل سنگین
هم‌زمان نگه داشته نشود. مدل quantized/FP16 جدیدی اختراع یا بدون منبع دانلود نشده؛
کاهش کیفیت از مدل OCR همراه، resolution/batch کمتر و fallback امن ناشی می‌شود.

## اجرای جدا، CPU و حافظه

`execution.py` از `ProcessPoolExecutor` با **spawn** و worker یک‌بارمصرف استفاده
می‌کند. آرایهٔ کامل تصویر از pipe عبور نمی‌کند؛ ورودی مسیر فایل/JSON است و خروجی
تصویری ابتدا داخل پوشهٔ خصوصی همان job نوشته می‌شود. پس از پایان، worker و مدل‌ها
آزاد می‌شوند. `desktop/launcher.py` پیش از main، `multiprocessing.freeze_support()`
دارد تا exe بسته‌بندی‌شده دوباره پنجره/سرور نسازد.

- threadهای ORT و OpenCV و متغیرهای BLAS محدود می‌شوند؛ affinity و اولویت پایین‌تر
  پردازشگر، در سیستم‌های پشتیبان اعمال می‌شود.
- بین تایل‌ها/نوارهای Medium و Low، `sleep(0.01)` اجرا می‌شود.
- سقف **جمع RSS والد و فرزندان ۲۳۰۴ MiB** هر ۱۵۰ms بررسی می‌شود؛ در عبور از بودجه،
  worker واقعاً terminate/kill و join می‌شود، نه فقط Future.cancel().
- در ویندوز، Job Object سقف committed memory هر worker را **۲۰۴۸ MiB** قرار می‌دهد؛
  اگر اعمال آن ممکن نباشد، worker به‌جای اجرای بی‌محافظ خطا می‌دهد.
- روی لینوکس RSS watchdog است، نه ادعای RLIMIT_AS قابل اتکا برای کتابخانه‌های native.
  نمونه‌برداری RSS تضمین ریاضیِ نبود هیچ spike کوتاه بین نمونه‌ها نیست.
- برای جلوگیری از تخصیص عظیم پیش از کنترل حافظه، سقف تصویر High/Medium/Low به‌ترتیب
  ۱۶/۱۰/۶ مگاپیکسل است. تصویر بزرگ‌تر با پیام تقسیم صفحه رد می‌شود؛ بی‌صدا کوچک
  نمی‌شود تا مختصات خراب نشود.
- ماسک‌های دشوار کلاسیک یک union دارند؛ ماسک تمام‌صفحه‌ای جدا برای هر glyph و
  نگهداری quad تمام‌صفحه‌ای برای هر خط حذف شده‌اند. ماسک‌های detector نیز تجمیع می‌شوند.

هدف ماندن در محدودهٔ ۲–۳ GiB و جلوگیری از قفل سیستم است؛ روی دستگاه فیزیکی i3 نسل۸
با ۸GB یا مدل واقعی LaMa تضمین عملکرد/کیفیتِ اندازه‌گیری‌نشده داده نمی‌شود.

## پیشرفت، ETA و لغو

| کار | پیشرفت | لغو |
|---|---|---|
| OCR | `GET /api/jobs/{id}/progress` | `POST /api/jobs/{id}/cancel?operation=ocr` |
| Clean و LaMa | `GET /api/jobs/{id}/clean-progress` | `POST /api/jobs/{id}/cancel?operation=clean` |
| Render | `GET /api/jobs/{id}/render-progress` | `POST /api/jobs/{id}/cancel?operation=render` |

پاسخ‌ها `fraction`, `stage`, `elapsedSeconds`, `etaSeconds` و در worker فعال
`resourceProfile`/`tileSize` دارند. ETA از پیشرفت مشاهده‌شده محاسبه می‌شود و قبل از
نمونهٔ کافی null است؛ مدت بارگذاری مدل قابل پیش‌بینی دقیق نیست. در React درصد، ETA
تقریبی و دکمهٔ «لغو پردازش» در مرحله‌های مربوط نمایش داده می‌شوند.

لغو پذیرفته‌شده، native inference در حال اجرا را با ازبین‌بردن فرایند متوقف می‌کند؛
نتیجهٔ نیمه‌کاره منتشر نمی‌شود و خروجی قبلی باقی می‌ماند. وضعیت `cancelled` ثبت و
درخواست اصلی با 409 پایان می‌یابد؛ UI آن را شکست با دیالوگ خطا نمایش نمی‌دهد.
پس از شروع commit کوتاهِ فایل‌ها، لغو دیررس دیگر پذیرفته نمی‌شود تا فایل‌ها نیمه
منتشر نشوند. درخواست مرحلهٔ اشتباه نمی‌تواند worker مرحلهٔ دیگر را لغو کند.

`T4_WORKER_MODE=inline` فقط برای تست‌های قدیمی با monkeypatch است؛ پیش‌فرض برنامه
همیشه فرایندی است. تست‌های مخصوص منابع صریحاً inline را خاموش می‌کنند و spawn و
کشتن worker واقعی را می‌سنجند.

## تست و شواهد

- ۲۷ تست جدید منابع: سیاست سه پروفایل، شکل/مقدار ماسک تایل‌ها، افت RAM، fixed-shape،
  fallback واقعی provider، ETA، پذیرش تصویر، RSS watchdog و مرز commit.
- زنجیرهٔ واقعی OCR → Clean → Layout → Render با spawn و مدل‌های همراه RapidOCR.
- لغو واقعی worker فعال برای OCR، Clean و Render؛ بقای فایل‌های قبلی و نبود worker
  باقی‌مانده پس از پاسخ تست می‌شود.
- تست صفحهٔ ۱۰۰۰×۵۰۰۰ (۵MP) با چهار کادر انگلیسی در Low: OCR و پاک‌سازی/رندر واقعی
  موفق شدند. در اجرای محلی نمونه، peak جمع RSS حدود OCR **۴۳۰ MiB**، Clean **۴۷۴ MiB**
  و Render **۳۶۴ MiB** ثبت شد. این اندازه‌گیری مدل LaMa/CTD نصب‌شده را شامل نمی‌شود.
- smoke test دسکتاپ اکنون با API واقعی داخل exe، worker فرایندی، OCR متن انگلیسی،
  پاک‌سازی، layout و رندر فارسی را می‌سنجد؛ تست صرفاً ساختن موتور یا صفحهٔ سفید نیست.

اجرای محلی:

```bash
.venv/bin/python -m pytest backend/tests -q -rs
npm test --prefix frontend
npm run build --prefix frontend
.venv/bin/python -m build backend --outdir dist/backend
```

در لینوکس بدون libGL، طبق `docs/inpainting.md` از OpenCV headless استفاده شود.
وابستگی Windows OpenCV تغییری نکرده و psutil به وابستگی پایه افزوده شده است.
